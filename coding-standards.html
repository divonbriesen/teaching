Coding Standards

These apply to code you write in any of my courses: HTML, CSS, JavaScript, and whatever comes after. They start with how you name things, because the names are most of the documentation. The rules for the pages you build live under Web Standards.

The Vicunadator checks the id and class rules on the Fizz Buzz pages. Everything else here is checked by people - your reviewers and me.

Names for Ids and Classes

  • Use lowercase letters, numbers, and dashes. Nothing else. first-name, not first_name or firstName.
  • That goes for every id and every class on the page, not just the ones in your form.
  • Dashes because CSS already uses them (font-size, margin-top), so your names read like the rest of the stylesheet.
  • Name what it is, not how it looks. error-message still makes sense when you change the color. red-text doesn't.
  • An id is used once on a page. A class can be used as often as you like.
  • A form field's id says what goes in it: first-name, middle-name, last-name.

Names in JavaScript

  • Variables and functions use camelCase: firstDivisor, checkDivision. Dashes don't work in JavaScript names (a dash is the minus sign), which is why the rule is different here.
  • A variable is a noun for what it holds. A function is a verb for what it does.
  • A true or false name reads like a question: isEven, hasMiddleName.
  • One-letter names are fine for a loop counter and nowhere else.

Names for Files and Folders

Lowercase, no spaces, and the name says what the file is: fizzbuzz0.html, not Page 1 FINAL.html. The rest of the file rules are in Web Standards.

Self-Documenting Code

Self-documenting code explains itself. You can read it and tell what it does without running it, and without a comment on every line. The names do most of the work. 

// Hard to read: what are 3 and 5, and what is x?
if (n % 3 === 0 && n % 5 === 0) {
  x += "w";
}

// Reads like what it does
if (checkDivision(counter, firstDivisor) && checkDivision(counter, secondDivisor)) {
  line += bothWords;
}
  • Put a number you might change in a named variable. When Fizz Buzz 3 adds another number, it's one new line, not a rewrite.
  • One job per function. If you need "and" to say what a function does, split it in two.
  • Write the code in the order a person would explain it: get the values, check them, build the message, show it.
  • Comments say why, not what. // count from start to end is just the loop again. // blank words stay blank, not "undefined" tells the reader something the code can't.
  • Self-documenting doesn't mean no comments. Explain the choices and rules the code can't show. Any class, id, div, or span you add only for styling gets a comment explaining it, like the one at the top of every page on this site.
  • Delete code you commented out. Don't leave it lying around.

A Quick Test

Cover the comments and read your code to a classmate. If they can say what each name holds and what each function does, it documents itself. If you have to explain a name out loud, rename it.
